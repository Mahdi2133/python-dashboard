# سامانه مدیریت کارگاه الکتروپمپ

**Electropump Workshop Management System** — یک وب‌اپلیکیشن محلی (Local Web Application)
برای ثبت، گزارش‌گیری و مدیریت روتین کارگاه الکتروپمپ.
روی یک رایانه/سرور سازمانی اجرا می‌شود و بقیه‌ی کاربران شبکه فقط با **مرورگر** به آن وصل می‌شوند.

```
             Company Network
                    │
          ┌─────────┴─────────┐
      PC User 1           PC User 2
       Chrome              Firefox
          └─────────┬─────────┘
                Server PC
          ElectropumpWorkshop.exe
                  Flask
                  SQLite
             instance/wells.db
```

روی رایانه‌های کاربر **هیچ نرم‌افزاری نصب نمی‌شود** — نه پایتون، نه Flask، نه SQLite.

---

## ۱. اجرای سریع (نسخه‌ی EXE)

```
dist\
├── ElectropumpWorkshop.exe
├── config.json
├── instance\wells.db      ← با Navicat for SQLite مستقیماً باز می‌شود
├── logs\
├── backups\
└── exports\
```

روی `ElectropumpWorkshop.exe` دابل‌کلیک کنید. خروجی کنسول:

```
================================================================
 ELECTROPUMP WORKSHOP MANAGEMENT SYSTEM
 سامانه مدیریت کارگاه الکتروپمپ
================================================================

Database:
  C:\Users\Mehdi Nasri\Desktop\Water supply\dist\instance\wells.db
  (SQLite — قابل باز کردن مستقیم با Navicat for SQLite)

Server running:
  http://127.0.0.1:5050

Other PCs on the same network:
  http://10.176.5.200:5050

Keep this window open.
Press Ctrl+C to stop the server.
================================================================
```

* مرورگر پیش‌فرض خودکار باز می‌شود (اگر از قبل باز باشد فقط یک تب جدید اضافه می‌شود).
* **IP شبکه hardcode نشده** و در هر اجرا از کارت شبکه خوانده می‌شود.
* این پنجره باید باز بماند؛ بستن آن سرور را متوقف می‌کند.

### دسترسی سایر رایانه‌ها
در Chrome یا Firefox آدرس `http://<IP سرور>:5050` را باز کنید.
آدرس دقیق در همان پنجره‌ی کنسول و نیز در صفحه‌ی **تنظیمات ← اطلاعات سیستم** نمایش داده می‌شود.

### فایروال ویندوز
اگر رایانه‌های دیگر وصل نشدند، در اولین اجرا برنامه خودش این پیام را می‌دهد:

```
[!] Network access may be blocked by Windows Firewall.
```

راه‌حل (بدون تغییر خودکار و خطرناک در فایروال):
1. **Windows Defender Firewall → Allow an app through firewall** و مجاز کردن
   `ElectropumpWorkshop.exe` برای شبکه‌ی **Private**؛ یا
2. در PowerShell با دسترسی Administrator:
   ```powershell
   netsh advfirewall firewall add rule name="ElectropumpWorkshop" ^
         dir=in action=allow protocol=TCP localport=5050
   ```

## ۲. تنظیمات — `config.json`

فایل کنار EXE قرار دارد و بدون تغییر کد قابل ویرایش است:

```json
{
    "host": "0.0.0.0",
    "port": 5050,
    "open_browser": true,
    "threads": 16,
    "database_filename": "wells.db",
    "database_path": "",
    "log_level": "INFO",
    "backup_keep": 30
}
```

| کلید | توضیح |
|---|---|
| `host` | `0.0.0.0` یعنی روی همه‌ی کارت‌های شبکه گوش می‌دهد (لازم برای دسترسی شبکه). `127.0.0.1` فقط همان رایانه. |
| `port` | پیش‌فرض **۵۰۵۰** (عمداً پورت پیش‌فرض Flask یعنی ۵۰۰۰ استفاده نشده). |
| `database_path` | خالی = `instance/wells.db` کنار EXE. می‌توانید مسیر مطلق دیگری بدهید (مثلاً درایو مشترک پشتیبان‌گیری‌شده). |
| `backup_keep` | تعداد پشتیبان‌هایی که نگه داشته می‌شود. |

پس از تغییر، برنامه را دوباره اجرا کنید.

## ۳. پایگاه داده

* موتور: **SQLite**، فایل: `instance/wells.db`
* **بیرون از EXE** — جایگزینی یا حذف EXE هیچ داده‌ای را از بین نمی‌برد.
* در Startup: اگر فایل وجود داشته باشد به همان وصل می‌شود؛ اگر نباشد ساخته می‌شود.
  **هرگز روی پایگاه داده‌ی موجود، پایگاه داده‌ی جدید ساخته نمی‌شود.**
* برای محیط چندکاربره فعال است: `journal_mode=WAL`، `busy_timeout=15000`،
  `foreign_keys=ON`، `synchronous=NORMAL`.
* مسیر فایل در **تنظیمات ← اطلاعات سیستم** و در کنسول نمایش داده می‌شود.

### باز کردن با Navicat
Navicat for SQLite → New Connection → SQLite → Existing Database File →
انتخاب `dist\instance\wells.db`.

## ۳٫۵ ورود به سامانه و سطح دسترسی

با اولین اجرا یک حساب مدیر ساخته می‌شود:

```
نام کاربری: admin
رمز عبور  : admin        ← در همان اولین ورود، تغییر آن اجباری است
```

**نقش‌های آماده**

| نقش | دسترسی |
|---|---|
| **مدیر سیستم** | همه بخش‌ها، از جمله مدیریت کاربران |
| **سرپرست** | ثبت و ویرایش داده و همه گزارش‌ها؛ بدون مدیریت کاربران و سیستم |
| **کاربر ثبت اطلاعات** | فقط ثبت رکورد جدید + مشاهده چاه‌ها و گزارش‌ها؛ **بدون ویرایش و حذف** |
| **فقط مشاهده** | دیدن رکوردها و گزارش‌ها، بدون هیچ تغییری |

نقش فقط یک «پیش‌فرض» است: در صفحه‌ی **کاربران**، با تیک زدن
«تنظیم دستی دسترسی‌ها» می‌توانید برای هر کاربر دقیقاً مشخص کنید کدام ۱۶ مجوز را
داشته باشد. تب‌هایی که کاربر مجوزشان را ندارد اصلاً برایش نمایش داده نمی‌شوند و
آدرس مستقیمشان هم با پیام فارسی رد می‌شود.

**مدیریت کاربران** (تب «کاربران») شامل:
* مشخصات شناسنامه‌ای: نام، نام خانوادگی، نام پدر، کد ملی، تاریخ تولد (شمسی)،
  تلفن، ایمیل، سمت، واحد
* کد کاربری، کد پرسنلی، رمز عبور، اجبار به تغییر رمز در اولین ورود
* **فعال / غیرفعال** — کاربر غیرفعال بلافاصله از سامانه بیرون انداخته می‌شود
  و دیگر نمی‌تواند وارد شود
* قفل خودکار پس از ۵ تلاش ناموفق (۱۰ دقیقه) و امکان باز کردن قفل توسط مدیر
* **مهلت ویرایش رکورد** — برای هر کاربر جداگانه تعیین می‌شود

## فرایند (Workflow)

ثبت اطلاعات دیگر یک نفر و یک فرم بلند نیست؛ یک **زنجیره** است. هر مرحله متولی
خودش را دارد و فقط همان بخش‌هایی را می‌بیند که به او مربوط است. رکورد تنها
زمانی در جدول رکوردها درج می‌شود که آخرین مرحله ثبت شود.

### مسیر

| مرحله | متولی پیشنهادی | فرم | در کدام عملیات |
|---|---|---|---|
| ۰ | شروع‌کننده | نوع عملیات: کشیدن یا نصب | هر دو |
| ۱ | مرکز آبرسانی | اطلاعات پایه + **علت خرابی** | فقط کشیدن |
| ۲ | مهندس امین بزرگمهر | بررسی کارشناس (نیاز به کشیدن دارد/ندارد + توضیحات) | فقط کشیدن |
| ۳ | مهندس مهدی یاقوتی‌نیا | عملیات و خرابی · موتور · پمپ · جدار چاه (اختیاری) | هر دو |
| ۴ | مهندس امین بزرگمهر | اقدام مورد نیاز + اطلاعات چاه و نصب | هر دو |
| ۵ | مهندس کاهانی | آزمایش پمپاژ · کابل و راه‌انداز · نتیجه بررسی | هر دو |

* **نصب** مستقیماً از مرحله ۳ شروع می‌شود؛ مرحله‌های ۱ و ۲ طی نمی‌شوند.
* **کشیدن** از مرحله ۱ شروع می‌شود تا علت خرابی پیش از هر اقدامی ثبت شود.
* **«اطلاعات پایه»** فقط یک‌بار پرسیده می‌شود — هر مرحله‌ای که زودتر برسد آن را
  پر می‌کند و از بقیه پرسیده نمی‌شود.

### مرحله‌ها به هم وابسته نیستند

هر کاربر با حساب خودش وارد می‌شود و **کارتابل** او دقیقاً می‌گوید چه چیزی باید
ثبت کند. لازم نیست منتظر مرحله‌های قبل بماند: کارگاه می‌تواند مشخصات موتور را
پیش از تصمیم کارشناس ثبت کند. اما اگر مرحله‌ای عقب‌تر هنوز ثبت نشده باشد، بالای
فرم **هشدار** داده می‌شود که کدام مرحله و متولی آن هنوز چیزی ثبت نکرده است.
فرایند وقتی کامل می‌شود که هیچ مرحله‌ی باقی‌مانده‌ای نداشته باشد — به هر ترتیبی
که ثبت شده باشند.

### قواعد مرحله ۴

اگر عملیات «کشیدن» باشد، ابتدا **اقدام مورد نیاز** پرسیده می‌شود:

| پاسخ | نتیجه |
|---|---|
| ویدئومتری · جمع‌آوری · بهسازی | «اطلاعات چاه و نصب» **بایگانی** و فرایند به مرحله بعد می‌رود |
| نصب الکتروپمپ جدید → تیپ الکتروپمپ الان انتخاب می‌شود؟ **بله** | فرم «اطلاعات چاه و نصب» نمایش داده و پر می‌شود |
| نصب الکتروپمپ جدید → **خیر** | فرم **موکول به بعد** می‌شود |

در عملیات «نصب» اصلاً این سؤال پرسیده نمی‌شود و فرم مستقیم نمایش داده می‌شود.

### علت خرابی در برابر «نصب مرتبط با…»

* عملیات **کشیدن** → فیلد **علت خرابی** فعال است و گزینه‌ی **«جمع‌آوری»**
  همیشه در آن هست؛ این گزینه **قفل** است و حذف یا غیرفعال نمی‌شود (فقط برچسبش
  قابل تغییر است).
* عملیات **نصب** → علت خرابی اصلاً پرسیده نمی‌شود و به‌جای آن **«نصب مرتبط با…»**
  می‌آید که با «تجهیز چاه جدید» شروع می‌شود و گزینه‌های دیگرش را در
  «مدیریت گزینه‌ها» اضافه می‌کنید.

### پر شدن خودکار فیلدهای «قبلی»

هر فیلدی که «قبلی» در عنوانش هست — تاریخ نصب قبلی، تیپ الکتروموتور قبلی، تیپ و
طبقه پمپ قبلی، عمق نصب قبلی — با انتخاب چاه از **آخرین عملیات همان چاه** خوانده
و پر می‌شود. آنچه عملیات قبلی نصب کرده، همان چیزی است که این عملیات پیدا می‌کند.
مقادیر **قفل نمی‌شوند**: با رنگ زرد مشخص می‌شوند و هر کدام قابل ویرایش است، چون
سابقه همیشه درست نیست و کسی که سر چاه ایستاده می‌داند.

### فرایندساز (تب «فرایندساز»)

* برای هر مرحله **متولی** را از فهرست کاربران انتخاب می‌کنید.
* بخش‌ها و فیلدها را با **کشیدن و رها کردن** از پالت به مرحله‌ها می‌دهید؛ هم
  یک بخش کامل و هم یک فیلد تکی (مثل «علت خرابی» که تنها فیلد مرحله ۱ است).
* برای هر مورد مشخص می‌کنید در «کشیدن»، در «نصب» یا در هر دو ظاهر شود، و
  اختیاری هست یا نه.
* تب **رصد فرایندها** مسیر هر فرایند را نشان می‌دهد: کدام مرحله ثبت شده، توسط
  چه کسی، چه چیزی بایگانی یا موکول شده، و آیا رکورد نهایی درج شده است.

### آنچه هر متولی می‌بیند

بالای فرم هر مرحله، یک پنل **فقط‌خواندنی** هست که کار همه‌ی مرحله‌های دیگر را
نشان می‌دهد: چه کسی، چه زمانی و چه چیزی ثبت کرده. بزرگمهر در مرحله ۲ علت خرابی
ثبت‌شده توسط مرکز آبرسانی را می‌بیند و بر اساس آن تصمیم می‌گیرد؛ کاهانی در
مرحله ۵ کار هر چهار نفر قبل را می‌بیند و بعد بخش خودش را پر می‌کند. این
اطلاعات به‌صورت متن برچسب‌دار نمایش داده می‌شود، نه فیلد — چون تغییرشان کار
این مرحله نیست.

**چاه یک‌بار انتخاب می‌شود.** در مرحله صفر که چاه مشخص شد، مرحله‌های بعد آن را
قفل‌شده و پرشده می‌بینند و دیگر جستجو نمی‌کنند.

هر مرحله بالای فرمش یک **راهنما** دارد: عنوان مرحله، شرحش، فیلدهای الزامی و
اینکه با زدن «ثبت و ارسال مرحله» فرایند به مرحله بعد می‌رود. زیر هر گروه
گزینه‌ای هم نوشته شده که یک مورد انتخاب می‌شود یا چند مورد، چطور انتخاب برداشته
می‌شود، و چند مورد تا الان انتخاب شده است.

### شروع فرایند

مرحله صفر هم **یک کارت در کارتابل** است، مثل بقیه‌ی مرحله‌ها — نه دکمه‌ای که
بالای هر صفحه بماند. فقط متولی مرحله صفر آن کارت را می‌بیند و فقط از همان‌جا
فرم «شروع فرایند» باز می‌شود؛ برای بقیه‌ی متولی‌ها نه کارتی هست و نه دکمه‌ای،
و درخواست مستقیم هم رد می‌شود. کار به آن‌ها می‌رسد، نه اینکه خودشان بسازند.

**چاه همان‌جا یک‌بار انتخاب می‌شود** و الزامی است — باید از فهرست چاه‌ها باشد،
نه یک نام تایپ‌شده. از آن به بعد هر مرحله‌ای که «اطلاعات پایه» را دارد، چاه را
قفل‌شده و پرشده می‌بیند و دیگر جستجویی در کار نیست.

### مستندات

در هر مرحله می‌توان **هر نوع فایلی** پیوست کرد — عکس، ویدئو، Word، PDF، Excel —
تا حداکثر ۶۴ مگابایت برای هر فایل. فایل‌های اجرایی (exe، bat، …) پذیرفته
نمی‌شوند.

تب **«مستندات»** همه‌ی فایل‌های همه‌ی فرایندها را یک‌جا نشان می‌دهد — با
فرایند، چاه، مرحله، بارگذارنده، تاریخ و حجم — قابل جستجو و دانلود. هم مدیر و
هم متولی‌ها به آن دسترسی دارند: عکسی که در مرحله ۳ گرفته شده همان چیزی است که
مرحله ۵ بر اساسش تأیید می‌کند، و نباید برای پیدا کردنش پنج فرایند را باز کرد.

### گزارش‌گیری متولی‌ها

متولی‌ها **جدول رکوردها** و **خروجی اکسل/CSV** را دارند تا بتوانند گزارش
بدهند، ولی همچنان ویرایش و حذف رکورد برایشان بسته است.

### دسترسی‌ها

سه مجوز تازه: **شرکت در فرایند (کارتابل)**، **مشاهده مسیر فرایندها** و
**فرایندساز**. نقش تازه‌ی **«متولی مرحله فرایند»** سه مجوز دارد: «شرکت در فرایند»،
«مشاهده رکوردها» و «خروجی گرفتن». با همین‌ها کارتابل، جستجوی چاه، پر کردن فرم
مرحله، بارگذاری مستند، مشاهده‌ی مستندات و گزارش‌گیری اکسل را دارد. چنین کاربری
سه تب می‌بیند — کارتابل، رکوردها، مستندات — و به ثبت اطلاعات، ویرایش رکورد،
فرم‌ساز، فرایندساز و کاربران دسترسی ندارد.

> خواندن *ساختار فرم* و *فهرست گزینه‌ها* به «ثبت رکورد» گره نخورده است: هر
> کسی که فرمی را پر یا رندر می‌کند به آن‌ها نیاز دارد. وگرنه برای اینکه یک
> متولی بتواند مرحله‌ی خودش را پر کند، مجبور بودید مجوز «ثبت رکورد جدید» را
> به او بدهید و در عمل کل تب ثبت اطلاعات با همه‌ی فرم‌ها برایش باز می‌شد.

مدیر سیستم همه‌ی مرحله‌ها را می‌بیند و مسیر همه‌ی فرایندها را رصد می‌کند.

### مهلت ویرایش رکورد

کاربر می‌تواند اشتباه خودش را اصلاح کند، ولی نه برای همیشه. مدیر برای هر کاربر
یک مهلت (بر حسب ساعت) تعیین می‌کند و از **لحظه‌ی ثبت هر رکورد** شمرده می‌شود:

* داخل مهلت → دکمه‌ی ویرایش فعال است و تاریخ پایان مهلت به کاربر نشان داده می‌شود.
* پس از مهلت → به‌جای دکمه‌ها نشانه‌ی 🔒 می‌آید، فرم فقط‌خواندنی می‌شود و پیام
  «برای تغییر با مدیر سیستم هماهنگ کنید» ظاهر می‌گردد.
* **حذف و بازیابی هم همین مهلت را دارند**، وگرنه کاربر می‌توانست رکورد را حذف و
  دوباره ثبت کند و عملاً مهلت بی‌اثر می‌شد.
* **مدیر سیستم هیچ‌وقت محدود نمی‌شود** و هر رکوردی را در هر زمان تغییر می‌دهد.
* پیش‌فرض «نامحدود» است، پس با به‌روزرسانی، رفتار هیچ کاربر موجودی عوض نمی‌شود؛
  مدیر باید آگاهانه برای کاربر مهلت بگذارد. برداشتن مهلت هم فوری اثر می‌کند.

مهلت به هر رکوردی که کاربر لمس می‌کند اعمال می‌شود، نه فقط رکوردهای خودش — یعنی
کاربر روی کار دیگران آزادی بیشتری از کار خودش پیدا نمی‌کند. اگر می‌خواهید کسی
اصلاً محدود نباشد، مهلتش را «نامحدود» بگذارید.

> جلوگیری در **سرور** انجام می‌شود؛ پنهان‌کردن دکمه فقط برای روشن‌بودن تکلیف
> کاربر است و درخواست مستقیم به API هم با خطای ۴۰۳ رد می‌شود.

**گزارش کارکرد هر کاربر** (دکمه‌ی 📊 روبه‌روی هر کاربر):
* ساعت ورود و خروج هر نشست، مدت حضور و IP
* رکوردهایی که ثبت کرده و رکوردهایی که ویرایش کرده
* فهرست کامل اقدامات (ثبت، ویرایش، حذف، خروجی، پشتیبان‌گیری، ورود، خروج)

> کاربران هرگز حذف فیزیکی نمی‌شوند؛ فقط غیرفعال می‌گردند تا سوابق و
> رکوردهایشان سالم بماند.

## ۴٫۵ مرجع چاه‌ها

فهرست چاه‌ها از دو فایل مرجع کارگاه ساخته می‌شود:

| فایل | نقش |
|---|---|
| **Well_Details** («لیست نهایی») | ۶۳۸ چاه شهری با «کد تاسیس» و «کلاسه» تمیز برای همه‌ی سطرها — **مرجع اصلی** |
| **total_wells** («GIS») | ۸۷۸ سطر شامل مراکز روستایی و **آدرس‌ها** — تکمیل‌کننده |

نتیجه: **۸۶۴ چاه یکتا**، همه با کد PM، ۸۷٪ با کلاسه، ۹۹٪ با مرکز، ۹۸٪ با آدرس.

* **کد PM** به شکل کامل `10/<مرکز>/<شماره>` ذخیره می‌شود.
* **نام‌ها یکتا هستند.** جایی که دو چاه واقعاً متفاوت هم‌نام‌اند (مثل «امام رضا 11»
  در دو مرکز)، اولی نام ساده را نگه می‌دارد — چون سوابق قبلی به همان ارجاع دارند —
  و بقیه با کد PM متمایز می‌شوند.
* هنگام راه‌اندازی، چاه‌هایی که فقط در املا فرق دارند **خودکار ادغام** می‌شوند:
  رکوردها به چاه اصلی منتقل، نام قبلی به‌عنوان نام مستعار ثبت، و ردیف تکراری
  غیرفعال می‌گردد. هیچ سابقه‌ای از بین نمی‌رود. سه قاعده کار می‌کند:

  | قاعده | نمونه |
  |---|---|
  | فولد فارسی (الف/آ، ی/ي، فاصله) | «ازاد شهر 2» = «آزاد شهر 2» |
  | ایندکس حرفی = ایندکس عددی | «ده غیبی یک» = «ده غیبی 1» |
  | ارقام کد PM + کلاسه‌ی یکسان | «گلشهر9 جدید» = «گلشهر9 جدید (BOT)» |
  | پسوند «قدیم»/«جدید» روی نام ثبت‌نشده | «امامیه 17( جدید )» = «امامیه 17» |

  قاعده‌ی دوم فقط روی **آخرین** واژه‌ی نام اعمال می‌شود، وگرنه «ده سرخ»، «چهار فصل»
  و «سه راه دانش» به‌اشتباه ادغام می‌شدند؛ «ده» هم اصلاً ایندکس شمرده نمی‌شود چون
  در این رجیستر همیشه به‌معنای *روستا* است و چاه شماره ۱۰ همیشه «10» نوشته شده.
  قاعده‌ی سوم هر دو کلید رجیستر را با هم می‌خواهد — دو چاه با ارقام PM یکسان ولی
  کلاسه‌ی متفاوت ادغام نمی‌شوند. قاعده‌ی چهارم فقط ردیف‌های **ثبت‌نشده** (بدون کد
  PM و تأییدنشده) را برمی‌دارد، یعنی نامی که موقع ثبت اطلاعات ساخته شده؛ چاهی که
  خودِ رجیستر «گلشهر9 جدید» نامیده، ردیف مستقل خودش را نگه می‌دارد. اگر دو چاه کد PM متفاوت داشته باشند، هرچقدر هم
  نامشان شبیه باشد جدا می‌مانند و کد PM کنار نام، تفکیکشان می‌کند.
* همین قواعد هنگام **جستجو**، **ورود از اکسل** و **افزودن چاه جدید** هم اعمال
  می‌شوند، پس نام تکراری نه در فهرست دیده می‌شود و نه دوباره ساخته می‌شود.
* نگاشت شماره‌ی مرکز به نام مرکز **از روی خود سوابق کارگاه** استخراج شده، نه حدس:
  هر چاهی که هم در فایل مرجع بود و هم در سابقه‌ی رکوردها، در برابر مرکزی که
  اپراتور نوشته بود شمرده شد (۲۱→دانشجو ۹۴٪، ۲۶→امامیه ۹۸٪، ۲۷→سوران ۸۳٪ و…).
  برای مراکز ۳۲، ۳۶ و ۴۴ شواهد کافی نبود، پس آن ۷ چاه بدون مرکز مانده‌اند.
* چاه‌هایی که فقط در اکسل عملیات دیده شده‌اند و در مرجع نیستند حذف نمی‌شوند؛
  در جستجو **بعد از** چاه‌های مرجع می‌آیند.

## ۵. تقویم شمسی

* تمام فیلدهای تاریخی Date Picker شمسی، RTL، با ماه‌ها و روزهای فارسی دارند
  (بدون هیچ کتابخانه‌ی خارجی).
* در حالت **ویرایش رکورد** هم فیلدهای تاریخ شمسی نمایش داده می‌شوند: هر تاریخ
  دو بار سریالایز می‌شود، `op_date` میلادی برای محاسبات و `op_date_j` شمسی برای
  فرم، و فیلدهای تاریخِ ساخته‌شده در فرم‌ساز نیز شمسی برمی‌گردند.
* **استاندارد ذخیره‌سازی:** تاریخ‌ها در پایگاه داده به‌صورت **میلادی ISO** (`op_date`)
  ذخیره می‌شوند و اجزای شمسی واردشده (`j_year/j_month/j_day`) نیز در کنار آن نگه داشته می‌شوند،
  تا تاریخ ناقصِ واردشده از اکسل قدیمی «اصلاح» نشود. رابط کاربری همیشه شمسی است.
* الگوریتم تبدیل (Borkowski) با الگوریتم سمت سرور یکسان است و برای سال‌های
  ۱۱۷۸ تا ۱۴۹۹ رفت‌وبرگشت بدون خطا تست شده است.

## ۶. ورود داده از اکسل

**ورود / خروج داده ← ورود از اکسل**

1. بارگذاری `.xls` / `.xlsx`
2. انتخاب شیت
3. **تشخیص خودکار سرستون‌ها** — سرستون‌های دوسطحی و سه‌سطحی
   (گروه «موتور»/«پمپ» بالای زیرعنوان‌ها) پشتیبانی می‌شوند و ستون‌های هم‌نام
   مثل دو «پلاک» بر اساس گروهشان از هم تفکیک می‌گردند.
4. اصلاح دستی نگاشت ستون‌ها
5. **بررسی آزمایشی (Dry-run)** بدون ذخیره
6. اجرای نهایی با تشخیص رکورد تکراری

رفتار در برابر داده‌ی ناسالم — هیچ داده‌ای دور ریخته نمی‌شود:

| وضعیت | رفتار |
|---|---|
| مقدار خارج از فهرست گزینه‌ها | گزینه‌ی «خودکار» غیرفعال ساخته می‌شود و برای بازبینی در «مدیریت گزینه‌ها» نشان‌دار می‌گردد |
| املای متفاوت (سعدابادی / سعد ابادی) | از طریق جدول نام‌های مستعار به گزینه‌ی صحیح نگاشت می‌شود |
| نام چاه ناشناخته | چاه «تأییدنشده» ساخته می‌شود؛ در «چاه‌ها» قابل تأیید یا ادغام است |
| متن در ستون عددی («نامعلوم») | آن ستون خالی ثبت و یک **هشدار** گزارش می‌شود؛ بقیه‌ی سطر ثبت می‌گردد |
| تاریخ ناقص | سطر ثبت می‌شود و کمبود تاریخ هشدار داده می‌شود |
| سال آینده (اشتباه تایپی منبع) | ثبت می‌شود و هشدار داده می‌شود — تصحیح خودکار انجام **نمی‌شود** |

### انتقال از نسخه‌ی قبلی (`localStorage`)
**ورود / خروج داده ← انتقال از localStorage** — دکمه‌ی «خواندن از این مرورگر»
کلید `electropump_records_v1` را پیدا می‌کند، یا JSON آن را دستی بچسبانید.

## ۱۱. امنیت

* **احراز هویت:** ورود با نام کاربری و رمز عبور؛ رمزها با
  PBKDF2-HMAC-SHA256 (۲۰۰٬۰۰۰ دور) و نمک تصادفی ذخیره می‌شوند — رمز خام
  هیچ‌جا نگهداری نمی‌شود. مقایسه‌ی رمز constant-time است.
* **کنترل دسترسی:** هر API و هر صفحه به یک مجوز مشخص گره خورده است؛
  کنترل روی **سرور** انجام می‌شود، نه فقط با پنهان‌کردن دکمه‌ها.
* **نشست:** کوکی HttpOnly + SameSite=Lax، انقضای ۱۲ ساعته‌ی بی‌کاری،
  و قفل حساب پس از ۵ تلاش ناموفق.
* **ساعت:** زمان‌ها **دقیقاً همان چیزی که ساعت رایانه نشان می‌دهد** ذخیره و بدون
  هیچ تبدیلی نمایش داده می‌شوند. پیش‌تر UTC ذخیره و ۳:۳۰ اضافه می‌شد، ولی این
  فقط وقتی درست است که *منطقه‌ی زمانی* ویندوز روی تهران باشد — که در بسیاری از
  رایانه‌های کارگاهی نیست، هرچند ساعت تسک‌بار درست نشان بدهد؛ نتیجه‌اش ساعت‌های
  ورودی بود که چند ساعت با واقعیت فرق داشت. حالا چنین وابستگی‌ای وجود ندارد.
  ایران هم از ۱۴۰۱ ساعت تابستانی ندارد.
  هنگام اولین اجرای این نسخه روی یک `wells.db` قدیمی، زمان‌های ثبت‌شده یک‌بار
  به ساعت محلی تبدیل می‌شوند تا سوابق قبلی همان‌طور که بودند خوانده شوند؛ این
  کار در جدول `app_meta` علامت می‌خورد و هرگز دوبار انجام نمی‌شود.
* **SQL Injection:** تمام کوئری‌ها از طریق SQLAlchemy با پارامتر bind می‌شوند.
  گزارش‌ساز فقط فیلدهای اعلام‌شده در `DATASETS` را می‌پذیرد.
* **CSRF:** روی همه‌ی درخواست‌های تغییردهنده فعال (Flask-WTF).
* **XSS:** خروجی تمام داده‌ها در جاوااسکریپت از `App.esc()` عبور می‌کند.
* **Validation:** نوع، بازه و الزامی بودن هر فیلد از تعریف فرم خوانده می‌شود.
* **Error handling:** هیچ traceback خامی به کاربر نمی‌رسد؛ پیام فارسی + ثبت در `logs/app.log`.
* **Audit log:** ایجاد، ویرایش، حذف، ورود، خروجی، پشتیبان و بازیابی ثبت می‌شوند.
* **آماده برای RBAC:** جدول `users` و ستون `user_id` در `audit_logs` موجود است؛
  ورود اجباری فعلاً غیرفعال است چون سامانه روی شبکه‌ی داخلی سازمان اجرا می‌شود.

> **هشدار استقرار:** ارتباط روی HTTP ساده است (بدون TLS)، بنابراین رمز عبور در
> شبکه رمزنگاری نمی‌شود. این سامانه برای **شبکه‌ی داخلی و مورد اعتماد شرکت**
> طراحی شده است؛ پورت آن را روی اینترنت باز نکنید.
